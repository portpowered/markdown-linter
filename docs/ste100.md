# Simplified Technical English checks

`text:ste100` is an opt-in pack with two error checks. It works with a customer-supplied vocabulary, not an embedded copy of the ASD dictionary. Compose it with `markdown:recommended` or `portos-defaults` when you want both policies. It uses the same configuration version, scopes, severity overrides, reasoned suppressions and baselines as other packs.

The [ASD overview](https://www.asd-ste100.org/STE_faq.html) describes a controlled dictionary and writing rules, including restrictions on meaning and part of speech. These checks enforce vocabulary membership and configurable lexical grammar patterns. They do not certify full STE100 compliance, parse parts of speech in sentences, or determine word meanings.

## Activation

```sh
marklint init --preset text:ste100 --output .marklint.yaml
```

Create `ste100-dictionary.yaml` in the document root before running lint. The preset deliberately requires a supplied dictionary. It does not silently accept a general English spelling dictionary.

```yaml
version: 1
extends: [markdown:recommended, text:ste100]
overrides:
  - id: text.ste100.dictionary
    options:
      dictionary-file: vocabulary/approved.yaml
      dictionary: [portos]
      technical-terms: [pagination context]
```

`dictionary-file` is relative to `--root`, including when the rule comes from an imported pack. It must name a local literal path inside that root. Absolute paths, parent traversal, URLs, globs and symlink escapes are rejected. The file is read once per rule execution. Missing, malformed, empty or contradictory dictionaries are operational errors (CLI exit 2); suppressions and baselines cannot hide them.

You can instead supply `dictionary: [use, the, api]` inline. Inline words, inline technical terms and file entries are combined. Vocabulary checking requires either inline dictionary words or a dictionary file. No implicit dictionary, stemming or synonym acceptance applies. Add every approved form deliberately.

## Dictionary format and word forms

```yaml
words: [to, will, the, use, do, a]
entries:
  - word: give
    forms: [gives, gave, given]
    part-of-speech: verb
    meaning: transfer to another person
  - word: check
    forms: [checks]
    part-of-speech: noun
technical-terms: [query shape]
alternatives:
  utilize: [use]
  inspect: [do a check]
```

`words` is a compact list of approved surface forms. `entries` groups forms under a base word. Each entry's `word` and `forms` are accepted, compared without case sensitivity. This example accepts `Gave`, but rejects `giving`, `giver`, and `utilizes`. Hyphenated words, apostrophes, Unicode letters, and digits inside names remain part of a token. Straight and typographic apostrophes are distinct surface forms; declare both if your policy accepts both. Numeric quantities alone are outside vocabulary checking.

An infinitive is a construction: `to give` uses the approved words `to` and `give`. The simple future similarly uses `will` and an approved base verb. A base word does not automatically approve derivations or every conjugation. Irregular forms belong in `forms`, alongside permitted regular forms. The [official verb guidance](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf) restricts verb forms and participle usage, so general lemmatization would be too permissive for acceptance.

`part-of-speech` and `meaning` document the vocabulary policy for editors. They are metadata, not contextual checks. Listing `given` accepts the token; an editor must still verify its permitted use. Use named grammar patterns for finite constructions you can identify reliably. A future contextual parser could use the metadata to distinguish noun and verb uses without changing this dictionary format.

`technical-terms` explicitly approves a complete phrase. Its individual words do not become approved elsewhere. Words must be separated by single spaces in the dictionary. Matching permits case differences, soft line breaks and emphasis. It stops at paragraph boundaries, punctuation, code, images and URLs. A technical term can contain a normally rejected word, consistent with ASD's distinction between general vocabulary and technical terms.

`alternatives` maps rejected single words to one or more approved words or phrases. For `utilize`, the finding suggests `use`; it still rejects `utilize`. Every suggested word must already be approved, or the entire suggestion must be a declared technical term. Keys must be rejected and unique without case sensitivity. These suggestions have no automatic fix because changing a word can change meaning or require restructuring. Add alternatives for rejected inflections explicitly, such as `utilized: [used]`, after approving the intended replacement form.

Use [the dictionary JSON Schema](ste100-dictionary.schema.json) for editor completion and structural validation. Runtime validation additionally checks word tokens, replacement membership and root boundaries.

Files accept exactly one YAML mapping with the four fields shown above. Unknown fields and invalid entries fail validation. This is the one supported format; no compatibility versions or automatic conversion rules are introduced.

## Grammar configuration

- `text.ste100.dictionary` accepts `dictionary`, `dictionary-file`, `technical-terms`, and `scope`.
- `text.ste100.grammar` accepts `max-sentence-words`, `forbidden-patterns`, and `scope`.

Both use `scope: prose` by default, covering paragraphs and headings. `scope: heading` restricts a rule to headings. Link labels are prose. Code, images, HTML syntax/comments, frontmatter and URL destinations are excluded. The same exclusions apply to grammar and vocabulary.

The preset uses a 25-word sentence limit and a finite contraction pattern. Sentence counting uses lexical word tokens separated by `.`, `!`, or `?`, within each paragraph or heading. This heuristic differs from the standard's complete counting rules for abbreviations, decimals, quantities and technical names. Set a project limit deliberately; this value is not a claim of full procedural-writing compliance.

```yaml
overrides:
  - id: text.ste100.grammar
    options:
      max-sentence-words: 20
      forbidden-patterns:
        progressive-adjust: '(?i)\b(?:is|are|was|were)\s+adjusting\b'
        perfect-adjust: '(?i)\b(?:has|have|had)\s+adjusted\b'
```

Patterns use Go's regular expression syntax. Names appear in diagnostics. Invalid expressions, blank names, expressions that match empty text, and nonpositive limits fail configuration validation. Overrides replace the entire options mapping. Include the preset's contraction pattern to retain it alongside custom patterns. Supply `{}` for `forbidden-patterns` when you want only the sentence limit. Regexes are finite lexical checks, not a general grammar parser.

## Tests and maintenance

The [example](../examples/ste100/.marklint.yaml) includes a deliberately small vocabulary to show the format. Replace it with your reviewed approved vocabulary and domain terms before adopting it for production documentation.

`pkg/rulepack/ste100_test.go` tests membership, explicit forms, infinitives, suggestions, phrase boundaries and source ranges. It also tests protected Markdown, file validation, root boundaries, grammar options, cancellation and composition. CLI tests confirm onboarding and operational versus policy exit codes. The default Make and CI checks run standard Go lint, race tests and a 95% module coverage gate.

Review dictionary changes like code changes. Confirm each approved form, meaning and part of speech against your standard. Test an accepted example and a near miss. Check that technical phrases do not approve standalone words. Keep alternatives as editorial guidance. Review ambiguous grammar and semantics separately.
